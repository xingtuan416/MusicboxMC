# 已知问题与限制

> 稳定基线：`0.4.0`；当前工作区：`0.4.5`（待用户实测）
> 最后更新：2026-11-15  
> 本文是后续修复工作的统一入口。`docs/status.md` 只保留当前状态摘要，不再重复完整问题清单。

## 使用方式

- `KI-*`：代码或运行时问题，可以定位到具体实现。
- `REL-*`：已经接受或暂时无法消除的产品限制，Release 页面也应引用这里。
- `OPS-*`：版本、规范、流程和仓库维护问题，不一定改代码。
- 级别：`P1` 需要优先处理，`P2` 应排期，`P3` 属于整理或说明问题。
- 状态：`待修`、`待确认`、`接受限制`、`待升级`、`已修复`、`部分完成`、`已改善`。
- 修复时在提交信息中引用编号，例如 `fix: prevent long-track stack overflow (KI-01)`。

## 已确认决策（2026-11-14）

- **D1**：全面跟进版本，目标是 Node 26 LTS、Electron 45 与当前构建/测试工具；不接受长期停留在旧主版本。
- **D2**：IPC 输出使用主进程发放的目录 token，渲染层不提交完整写盘路径。
- **D3**：Minecraft 兼容性按 Litematica 的 v6 数据结构与 DataFixer 能力表述，固定数据版本保持不变。
- **D4**：主进程发生未捕获异常时记录并退出，不继续运行。
- **D5**：Windows CI 每个 PR 跑 `check + dist:dir`，tag/手动发布时跑完整打包；UI 验证仍先保持本地。
- **D6**：允许清理旧 `release-*` 产物，并把 `*.iml` 加入忽略规则。
- **D7**：强制合并的全曲 compact/staged 选择暂缓，等解释后再决定。
- **D9**：投影里的轨道注释默认开启，并作为独立区域导出；全曲合并成一条主线时不再宣称独立主音轨，玩家站位取该主线 Z 中点（2026-11-15）。
- **D8**：稀疏音轨借道是可选开关（默认开启），只在未合并布局 Z > 30 格时尝试，且必须实测——合并/借道都可能让 Z 更宽，不能假设变窄。
- **D10**：首音很晚的轨道默认从上方最近的轨道取电（`GenerateOptions.laneRide`，默认开启），跨几行就用几个中继器、每行 +1 红石 tick（2026-11-15；第七轮由“只借相邻两行”改为跨行走廊）。

## 代码与运行时问题

### KI-01：超长单轨在导入分析时栈溢出

**级别**：P1  
**状态**：已修复（0.3.0）

**现象**：一条音轨的音符数达到约 12.5 万时，选择该 MIDI 后会在“分析”阶段直接失败，尚未进入布局生成。

**证据**：

- `src/main/analyze.ts:31-32` 对整条轨展开 `Math.min(...ticks)` / `Math.max(...ticks)`。
- `src/core/layout/index.ts:332` 对固定乐器轨再次展开 `Math.max(...midis)`。
- 实测单轨 125,000 个音符返回 `RangeError: Maximum call stack size exceeded`。
- 同类的 `warnings.push(...w)` 和合并轨的 `notes.push(...input.notes)` 也会在超长轨上溢出。
- `0.2.3` 已经在命令后端移除了同类展开，但上述位置仍然保留。

**影响**：文件无法导入，界面只能看到通用失败信息。正常歌曲很难达到这个规模，但项目已经支持 46k 音符的曲目，继续增长后会触发。

**修复方向**：改为一次循环扫描或 `reduce`；为分析阶段和固定乐器跨度检查各加一个超长轨回归测试。

### KI-02：主进程仍信任渲染层提供的输出路径和块配置

**级别**：P1  
**状态**：已修复（0.3.0）

**现象**：`options.ts` 明确写着“渲染层不可信”，但 `song:generate` 仍把渲染层传来的路径直接交给写盘函数。

**证据**：

- `src/main/index.ts:130-136` 接受任意非空 `outputPath`。
- `src/main/generate.ts:386` 直接 `writeFileSync(outputPath, buffer)`。
- `assertFile()` 只检查“文件存在”，不限制 `.mid` / `.midi`。
- `src/main/options.ts:65` 对 `blocks` 只判断是对象，随后直接强转为 `BlockOverrides`。
- `shell:reveal` 也接受任意存在的路径。

**影响**：当前渲染层不加载远程页面，并启用了 sandbox 和 context isolation，实际攻击面有限。但一旦渲染层出现 XSS 或被替换，恶意调用可以向任意可写路径覆盖文件。它与项目声明的 IPC 边界不一致。

**修复方向**：输出路径必须来自主进程目录对话框或短期授权令牌；限制扩展名和父目录；对 `blocks` 做逐字段白名单校验。主进程只根据授权结果写盘，不接受渲染层重新提交的绝对路径。

### KI-03：`SPATIAL_DRIFT` 警告无法定位

**级别**：P2  
**状态**：已修复（0.3.0）

**现象**：用户能看到“多轨对齐出现偏差”，但不知道是哪条轨、哪一段，也没有“在红石布线里定位”按钮。

**证据**：

- `src/core/layout/types.ts:117` 只包含 `tick` 和 `drift`。
- `src/core/layout/track.ts:227` 生成警告时没有携带 `trackIndex`、`x` 或 `z`。
- `src/renderer/warningText.js:124` 只能通过坐标或 `trackIndex` 查找位置。

**影响**：这条警告对普通用户几乎不可行动；在 `Rush E` 等容量不足的曲目上会一次出现大量相同提示。

**修复方向**：警告增加 `trackIndex`、`zBase`、`x`，并考虑把同一段连续偏差聚合而不是逐音群重复。

### KI-04：关于 `package.json` 的注释与安装包事实相反

**级别**：P3  
**状态**：已修复（0.3.0）

**证据**：

- `src/main/index.ts:183` 写着 `package.json` 不属于打包产物。
- `package.json:70-73` 明确包含 `package.json`。
- `release-0.2.5/win-unpacked/resources/app.asar` 内确实存在根目录 `package.json`。

**影响**：当前版本读取依赖它，功能没有问题；注释会误导后续维护者删除或改坏版本来源。

**修复方向**：修正注释，并说明为什么包内保留清单文件。

### KI-05：强制合并会被单个超宽和弦切换成全曲 staged 布局

**级别**：P2  
**状态**：待确认（D7，0.3.0 暂不处理）

**证据**：

- `src/core/layout/forced.ts:198` 使用 `groups.every(...)` 决定 `compact`。
- 只要全曲有一个音群超过紧凑容量，所有音群都会改用两行间隔的 staged fallback。
- 该模式还会给全曲增加统一分支延迟。

**影响**：一个局部极端和弦会改变整首曲子的结构尺寸和启动等待，用户很难从参数上预期。它是当前为了布线一致性做的全局选择，不一定应改成逐音群切换。

**修复方向**：先确认产品语义。如果保留全局切换，界面和文档必须明确说明；如果改成本地切换，需要重新验证主干高度、功率续接和全曲延迟一致性。

### KI-06：主进程吞掉未捕获异常后继续运行

**级别**：P2  
**状态**：已修复（0.3.0）

**证据**：`src/main/index.ts:244` 只把 `uncaughtException` 发给渲染层，没有退出、重启或恢复状态。

**影响**：Node 的默认终止行为被覆盖，主进程可能在内部状态已经损坏时继续接受操作。界面上只显示一条日志，用户会以为应用仍然正常。

**修复方向**：确认是否要“记录后退出”；更安全的做法是记录、通知界面并退出，至少不能静默继续执行关键 IPC。

## 版本、规范与流程问题

### OPS-01：Node 版本声明与实际打包能力矛盾

**级别**：P1  
**状态**：已修复（0.3.0）

**证据**：

- `package.json` 声明 `"engines": { "node": ">=20" }`。
- 本机 Node 24.22.2 执行 `npm run dist` 时，electron-builder 生成 `.ico` 的工具报 `WebAssembly.Memory(): could not allocate memory`。
- 同一流程在 Node 22.23.2 下成功。
- 项目文档和 CI 也只明确验证 Node 20 / 22。

**影响**：按 `engines` 安装 Node 24 的贡献者会遇到一个与业务代码无关的打包失败，错误信息也无法指向版本约束。

**结果**：electron-builder 升到 `26.18.0` 后，Node 24 已成功生成 NSIS 安装包和便携 zip；随后开发基线继续升级到 Node 26 LTS，`engines` 改为 `>=26`，Node 26.13.1 下的 typecheck、测试、Windows 解包打包、IPC 冒烟和界面验证均通过。首次构建时图标包下载曾因网络中断失败，重试后通过，不再是 WASM 分配错误。

### OPS-02：运行时和工具链长期停留在旧主版本

**级别**：P2  
**状态**：已修复（0.3.0）

**0.3.0 结果**：

- Node 升级到 26 LTS，CI 不再运行已停止维护的 Node 20；`@types/node` 同步为 26.6.6。
- Electron 从 `33.4.11` 升到 `45.3.2`；electron-builder 升到 `26.18.0`。
- Vitest 升到 `5.1.0`，Vite 升到 `8.3.8`，ESLint 升到 `10.15.0`。
- TypeScript 7.0.2 已采用，并保留 `@typescript/typescript6` 作为 `typescript` 别名供 ESLint 使用；构建与类型检查显式调用 `typescript7/bin/tsc`。
- `tsconfig` 从已弃用的 `moduleResolution: node` 迁移到 `node16`。
- 仓库加入 Dependabot 周更分组。
- `@tonejs/midi 2.0.28` 仍是 npm 最新版，无需升级。

### OPS-03：补丁发布掩盖了维护债务

**级别**：P2  
**状态**：已处理（0.3.0 运行时升级 + Dependabot）

**0.3.0 结果**：运行时、构建器、测试框架和 CI 已整体升级，Dependabot 负责后续分组更新。该问题不再保留为未决债务。

**后续规则**：每个 Release 前检查一次 Node/Electron/测试框架的支持状态；大版本升级不与无关功能混在同一提交。

### OPS-04：支持范围应按 Litematica v6/DataFixer 能力表述

**级别**：P3  
**状态**：已修复（0.3.0）

**结论**：固定 `MinecraftDataVersion = 3700`、litematic `Version = 6` 不是缺陷，无需为了追随游戏版本改成动态 DataVersion。需要改的是 README 把“支持范围”错误地等同于 Minecraft 版本。

**证据**：

- `src/core/litematic/build.ts:30-31` 固定 `MinecraftDataVersion = 3700`、litematic `Version = 6`，对应 1.20.4。
- 当前 Litematica 26.3 分支定义 `SCHEMATIC_VERSION = 7`，读取时接受 `Version 1..7`，所以 v6 仍在支持范围：
  [LitematicaSchematic.java](https://github.com/sakura-ryoko/litematica/blob/26.3/src/main/java/fi/dy/masa/litematica/schematic/LitematicaSchematic.java)
- 当文件 `MinecraftDataVersion` 低于当前游戏时，它对 blockstate palette、方块实体和实体执行 Vanilla DataFixer 升级。
- 用户已实机验证 1.17.1–26.3 两端的对应组合，但支持条件应写成“文件结构 + Litematica 读取能力”，不是“游戏版本天然兼容”。

**影响**：用户会以为生成器跟随每个 Minecraft 版本更新，或误把加载失败归因于 `.litematic` 内容错误；实际取决于使用的 Litematica 版本是否接受 v6、是否执行 DataFixer，以及是否认识所用方块状态。

**0.3.0 结果**：

1. 保留 `Version 6 + DataVersion 3700`，没有引入动态 DataVersion。
2. README 中英文都已改为“输出 litematic v6，由对应 Litematica 读取并通过 DataFixer 升级旧数据版本”。
3. 保留用户实机验证的 Minecraft 1.17.1–26.3 范围，并把它绑定到对应 Litematica 组合。
4. 不加入铜制 trumpet 的理由不变：会破坏 v6 基线可用的方块集合。

### OPS-05：许可证展示不统一

**级别**：P3  
**状态**：已修复（0.3.0）

**证据**：

- `package.json` 是 `GPL-3.0-only`。
- README 徽章是 GPL-3.0-only。
- `src/main/index.ts:189` 的关于页硬编码为 `GPL-3.0`。
- `LICENSE` 是标准 GPLv3 文本。

**影响**：`GPL-3.0` 在 SPDX 语境下不如 `GPL-3.0-only` 明确，可能被理解为允许后续版本。项目自己的审查规则也要求不得出现“or later”的暗示。

**修复方向**：关于页统一显示 `GPL-3.0-only`，并加一条断言。

### OPS-06：独立 Java 校验器没有进入自动测试

**级别**：P2  
**状态**：已修复（0.3.0）

**证据**：

- `test/fixtures/VerifyLitematic.java` 被文档描述为格式权威。
- `test/litematic-roundtrip.test.ts:145-162` 只读取预置 `tiny.litematic` 并比较固定期望值，不执行 Java。
- 现有测试能防止自家实现漂移，但不能发现 Java 校验器本身与当前规范不一致。

**影响**：格式回归仍主要依赖人工运行一次 Java。CI 不会因为 Java 校验器失败而失败。

**修复方向**：在 CI 或本地 `npm run check` 的可选步骤中执行 Java；如果环境没有 JDK，至少把“未执行 Java”明确标成跳过原因，而不是让文档暗示已自动验证。

### OPS-07：Issue/PR 模板与实际流程脱节

**级别**：P3  
**状态**：已修复（0.3.0）

**证据**：

- `.github/ISSUE_TEMPLATE/bug_report.yml` 的版本占位仍是 `0.1.0`。
- `.github/PULL_REQUEST_TEMPLATE.md` 只列 `lint`、`typecheck`、`test`、`build`。
- `.github/CONTRIBUTING.md` 和 CI 的统一闸门已经是 `npm run check`，其中还包含 `format:check`。

**影响**：贡献者按模板操作会漏掉格式检查；Issue 示例版本落后五个补丁版本。

**修复方向**：模板改成 `npm run check`，版本占位改成 `<version>` 或当前版本。

### OPS-08：状态、变更日志和 Release 说明存在三套重复叙事

**级别**：P3  
**状态**：已处理（0.3.0 增加 `release:notes`）

**现象**：同一个修复会同时写进 `docs/CHANGELOG.md`、`docs/status.md` 的“已完成”和 GitHub Release body；Release 的已知限制又是第四份手工副本。`docs/status.md` 还把 GitHub 数据库 ID 写成 `run #43563003877`，与真正的 run number 不是一回事。

**影响**：内容容易漂移，发布时需要人工同步多处。这次的已知限制已集中到本文，但状态文档与 Release body 仍可能重复。

**0.3.0 结果**：新增 `npm run release:notes`，从 `docs/CHANGELOG.md` 与本文的限制章节生成 Release body 草稿。下载表、文件大小和校验和仍由发布步骤追加，因为它们依赖实际构建产物。

### OPS-09：本地产物目录膨胀且部分本地文件未纳入忽略规则

**级别**：P3  
**状态**：已修复（0.3.0）

**0.3.0 结果**：

- `*.iml` 已加入 `.gitignore`。
- `release-0.2.3/`、`release-0.2.4/` 和 `release/` 中 0.2.1–0.2.4 的旧安装包已删除。

## 产品与游戏内已知限制

这些限制来自 Release 说明和设计文档，当前不具备简单的代码修复条件，或属于有意取舍。

### REL-01：长曲画布拖动不跟手

**级别**：P2  
**状态**：已改善（0.3.0 用户实测通过）

长曲预览原先每次拖动都会重新扫描全部预览格并在每帧重设画布缓冲区。0.3.0 为每个结果缓存非空格统计，只在画布尺寸变化时重建缓冲区；用户实测《鸟之诗》长曲拖动已通过。

后续仍保留为性能回归观察项。若未来更长的曲目再次出现卡顿，再评估可见区域离屏缓存或降低采样密度；这些改动必须继续由真实界面手感验证。

### REL-02：命令播放的额外运行要求

**级别**：P2  
**状态**：接受限制

命令播放需要：

- 命令方块已启用；
- 粘贴时保留方块实体 NBT；
- 整个结构位于已加载区块；
- 世界的 `maxCommandChainLength` 大于生成的链长；
- 客户端声音池能承受峰值同刻音符数。

命令播放不消除区块加载要求，只把电路变成更紧凑的命令链。

### REL-03：同一投影文件粘贴出的播放器共用命名空间

**级别**：P2  
**状态**：接受限制

同一投影文件粘贴多次会复用文件内的计分板与 storage 路径。同时使用多个播放器时，请分别检查并导出每份投影。停止播放会撤销本机剩余音符，已经发出的声音会自然播完。

### REL-04：超过紧凑路径容量的和弦在强制合并下使用 staged 两行总线（最多 27 音）

**级别**：P2  
**状态**：接受限制

两个容量不同：普通布局的单列容量是 `2×dMax+1`（dMax 14 → 29 音，`src/core/layout/model.ts:54-57`），超过就拆轨（`POLYPHONY_EXCEEDED` + `TRACK_SPLIT`）；强制合并的紧凑路径只到 `min(2×dMax+1, 27)`（`src/core/layout/forced.ts:190-198`），因为紧凑列由入口/上一组经一格红石粉供电、根到达强度是 14 而不是 15，每侧只能 13 行。强制合并为了保持单主轴不能拆轨，超过这个数时**整条主线**退回两行间隔的 staged fallback。该路径会增加结构高度和全曲统一延迟，但不会丢音。

### REL-05：超大电路不保证区块加载、性能和听距

**级别**：P2  
**状态**：接受限制

生成器只描述静态方块和时序，不仿真：

- 区块加载和卸载；
- Minecraft 红石更新顺序；
- 客户端声音池；
- 音符盒听距；
- 服务器性能。

`Rush E` 这类超大电路即使生成成功，也可能因区块加载或声道距离听起来不完整。这是游戏内运行条件，不是 litematic 文件损坏。

### REL-06：不支持 1.21.2+ 铜制 trumpet，输出目标仍是 1.20.4

**级别**：P2  
**状态**：接受限制

项目使用 1.20.4 数据版本和 16 种经典音符盒乐器，不加入 1.21.2+ 的铜制 trumpet 变体。加入新方块会牺牲 1.17.1–1.20 的兼容性，目前没有这个计划。

### REL-07：布局不是红石模拟器

**级别**：P2  
**状态**：接受限制

`layout()` 生成静态方块和时序描述，不模拟 Minecraft 的方块更新顺序、红石网络隔离、区块加载或性能。强制合并有独立图校验，但同样不是完整游戏模拟。所有输出仍需在游戏中验证。

### REL-08：主音轨的“响”只能靠距离，音符盒音量固定

**级别**：P2  
**状态**：接受限制（0.4.0）

**现象**：选轨页显示“平均力度 94%”这类数字，容易被理解成游戏里会真的更响。

**事实**：Minecraft 红石音符盒的输出电平固定，MIDI velocity 无法写进投影。主音轨的优势只有两条：它只按力度被选出来（平局看音符数，再看文件顺序），并且玩家就站在它的红石粉那一行（布局把那一行固定在 z = 0），因此它离玩家最近、衰减最小。

**已做的处理**：选轨页主音轨卡片底部固定一行说明“力度只决定选哪条轨，红石音符盒的音量固定，听感差异来自距离”。

### KI-07：智能推荐和检查曾重复编码整份投影

**级别**：P3  
**状态**：本地已修复（2026-11-25）

推荐在后台实测候选布局，选出路线后返回。检查生成预览和诊断。输入文件与生成选项匹配时，导出复用检查的布局，只编码一次。候选仍使用真实布局测量，超长曲目可能需要等待。

### KI-08：借道只按整轨借入，不能逐音挑稀疏音符

**级别**：P3  
**状态**：接受限制（0.4.0 初版）

**现象**：稀疏音轨整体借到一条宿主轨道，或几条零碎轨合成一条收集轨；不会把“一条只会偶尔出现的伴奏轨”里那几十个音分别塞进不同轨道。因此当宿主列的容量在某个时间点被占满时，整条客串轨只能保持独立轨道（计划里体现为 `kept`）。

**原因**：现有布局是“一条输入轨 → 一条主线”，逐音挑需要把布局改成先规划轨道、再按列装音，属于结构改造；用户已确认 0.4.0 只做整轨借入。

**影响**：极稀疏但时间点分散的轨仍可能保留独立轨道，Z 不如理论最小值。表现是检查页出现“装不下，保持独立轨道”。

**修复方向**：把 `src/core/layout/index.ts` 的轨道循环拆成“规划轨道 → 每列装音”，客串以音符为单位入列；同样必须实测 Z，且要保留 TRACK_SPLIT 的溢出行为。

### KI-09：主轨居中会把多轨 Z 拉宽（根因是音符盒被平移两次）

**级别**：P3  
**状态**：已修复（0.4.0 第九轮）

**现象**：打开智能分流或手动选过主轨后，多轨布局的 Z 跨度明显变大。dMax 8 的 16 轨夹具从 40 格变成 56 格；27 轨《鸟之诗》（dMax 14）从 82 格变成 122 格（+49%）。两例都因此跨过 48 格听距阈值，触发本来不需要的强制合并。

**原因（第九轮查清）**：不是“副轨分到两侧所以更宽”，而是一个内存别名 bug。`src/core/layout/track.ts` 的 `putNote` 把同一个 `notePos` 对象既交给 `place()` 又存进 `PlacedNote.notePos`，而 `place()` 原本直接返回传入的格子对象、不克隆。居中时 `translateTrackZ()` 先平移 `placement.pos.z`（同一对象）再平移 `note.notePos.z`，于是**每个音符盒被平移了两次**，离开自己的红石行。Audit 探针实测：不居中的布局 346 个音符 0 偏移；一旦带 `laneOrder`，346/346 全部偏移、最远 19 格，跨区域重复格子出现 571 个。红石模拟器里这种布局一个音都不响。

**已做的处理**：`src/core/layout/placement.ts` 的 `place()` 改为 `return { pos: { ...pos }, ... }`，并加注释说明调用方会保留传入的格子引用、之后整体平移轨道。修完后同一条曲目居中与不居中的宽度完全相同（夹具 40 / 40，鸟之诗 82 / 82，合并后 38 / 38），`SMART_CENTER_WIDENS` 不再触发，`test/centerLead.test.ts` 的两条断言相应改成“居中不改变宽度”；新增 `test/layoutGeometry.test.ts` 守住 `notePos` 与方块位置、行内不重复、居中不改宽度、以及居中布局跑红石模拟器 346/346 音符准点。

**保留的东西（第十一轮改写）**：`SMART_CENTER_WIDENS` 与“重测一次不居中布局”的守卫已经删掉。原因有两条：修掉别名 bug 之后居中根本不改变宽度，守卫抓不到东西；第十一轮改成“玩家站主轨那一行、其余轨道按优先级铺到两侧”之后，“关掉居中能省听距”这个建议本身就不成立了。`GenerateOptions.centerLead` 保留但语义变了——它现在只决定轨道是按优先级排还是按文件顺序排，玩家始终站在主音轨的红石粉那一行（见 KI-15）。

**边界**：居中会让注释牌与玩家站位的 Z 坐标随之改变（这是应有行为）；`centerLead: false` 与历史布局的逐字节相同性在第十一轮之后不再成立——对称放置改变了所有轨道的 Z 分配，`test/centerLead.test.ts` 现在断言的是“按文件顺序铺、但玩家仍站主音轨那一行”。

### KI-10：合并后主音轨语义失效，投影里也看不出哪条是主音轨

**级别**：P2  
**状态**：已修复（0.4.0 第四轮）

**现象**：用户导入《鸟之诗》后指出两件事——投影（`.litematic`）里没有任何标记能说明哪一条轨道是主音轨；而且一旦开启任一种合并，界面上的“主音轨”仍按合并前的源轨宣称，强制合并后整曲只剩一条主线，“主轨居中 / 玩家站在主轨上 / 听感中心”这些说法都不再成立。

**原因**：主轨只存在于界面状态里（`smartSelection.leadTrackIndex`），从未写进投影；`TrackSkeleton` 只有 `trackIndex`，合并或借道之后无法反查一条轨道包含哪些源轨，因此合并后也只能继续显示源轨编号。强制合并走 `buildForcedLayout`，返回单条 `trackIndex: -1` 的主线，语义上已经没有“主轨轨道”。

**已做的处理**：新增 `src/core/layout/annotation.ts` 与 `GenerateOptions.annotateLanes`（默认开，配置页「投影注释」开关）。每条轨道在电路西侧 3 格立一块 `minecraft:oak_wall_sign`（朝 -X，从起点正面可读），底座金色＝主音轨、铜色＝副轨；牌面写「主音轨 / 轨 N · 力度 P% / 站这里」，副轨写「副轨 / 轨 N / 力度 P% / 距主轨 N」；全曲合并成一条主线时写「全曲主线 / 站这里 / Z 中段」。注释单独成一个区域（`trackIndex: -2`），可以在 Litematica 里单独删除或移动。`TrackSkeleton.sourceIndices` 让生成阶段按源轨反查主轨所在轨道；单条主线时第 6 步主音轨行改为“全曲合并成一条主线，没有独立主音轨”，玩家站位取主线 Z 中点。

**边界**：牌面 4 行、每行 15 字符以内，超过 3 条源轨时退化成「共 N 轨」；命令播放后端没有轨道排布，开关显示为不适用；注释让 X 多 3 格（`LayoutMeasure.annotatedExtraX`），不影响 Z 宽度与合并判定。

### KI-11：首音很晚的轨道要铺几千格中继器“车头”，长曲里最容易被区块加载打断

**级别**：P2  
**状态**：已修复（0.4.0 第五轮）

**现象**：用户导入《鸟之诗》后反馈——“生成出来的轨道假如说在前面没有音后面有，总是会自己去计算音在哪，前面放中继器很稀疏却后面连着放，因为区块加载的特殊性总是会导致出现这条轨道‘断点’”。听感上是中后段某几条轨道不再发声，像是多轨不同音。

**原因**：每条轨道都从 X = 0（共享参考线的起点）独立递推到自己的第一个音；首音很晚的轨道于是要在前面一路铺中继器与红石粉。27 轨《鸟之诗》实测：36% 的方块（36134 / 100956）位于各轨道首音之前，其中 3511 个是中继器，最长的一条首音在 X = 2474、前面铺了 4948 格。整曲 X = 2678 格约 168 个区块，只用命令方块或只靠视距，玩家站起点只能听到 4% 的音符。时间轴本身没有问题：`src/core/sim/redstone.ts` 逐 tick 执行后 7410/7410 个音符全部落在计划 tick。

**已做的处理**：`src/core/layout/track.ts` 的轨道取电（`GenerateOptions.laneRide`，默认开，配置页「相邻轨道取电」开关）让“前面一段没有任何 tap”的轨道从上方最近的轨道取一次电——在 `(x, zBase)` 落一个红石粉，然后把这条轨道与宿主之间每一行都放一个同向中继器（facing 朝宿主一侧）引上来，再照常布线。27 轨《鸟之诗》实测 100956 → 70410 方块（-30%，17 条取电）；同乐器合并后 54040 → 49174（3 条，Z 39 / 8 轨不变）。`placed` 的时间轴逐音符不变；`test/laneRide.test.ts` 复跑模拟器，不合并与合并两种布局下夹具 346 个音符仍全部准点。打开开关不改变旧调用方的布局：`laneRide` 不传时走历史路径。

**为什么中继器列可以跨行**：中继器只从自己的输入面读信号、输出固定 15，所以一列同向中继器能把信号带到任意一行，而**不会**点亮它侧面经过的那些行（红石粉相邻即连，中继器不是）。跨 `n` 行就多 `n` 个中继器、多 `n` 个红石 tick，取电点因此按 `prevRt = 宿主该格 rt + 走廊长度` 计入时间轴；搜索时还要求走廊格左右不挨着中继器，否则会被旁边的二极管锁定。

**边界**：走廊只能竖着走（红石粉在 T 形交叉处不给垂直分支供电，横向借电仍需中继器拐角、会多点亮一行，2 层结构也没有第三层做高架）；被借的那段必须是宿主轨道的红石粉（无 tap 的车头即满足）；开头就有音的轨道不受影响；走廊若撞上本轨道自己的分支行（两方块叠一格会静默失效）就退回自建车头；命令播放后端没有轨道排布，开关显示为不适用；区块加载的**时间顺序**仍不模拟（见 `REL-05`），取电只是让车头不再依赖长距离加载。

### KI-12：开发版与别的 Electron 应用共用 `%APPDATA%\Electron`，第二次启动报缓存拒绝访问

**级别**：P2  
**状态**：已修复（0.4.0 第六轮）

**现象**：`npm start` 时终端刷出 `[ERROR:net\disk_cache\cache_util_win.cc:25] Unable to move the cache: 拒绝访问 (0x5)`、`Unable to create cache`、`Gpu Cache Creation failed: -2`，每条重复好几次。

**原因**：未打包运行时 `app.getName()` 是 `Electron`，`userData` 因此落在 `%APPDATA%\Electron`——机器上任何别的未打包 Electron 应用都用这个目录。当时同时有三个实例在跑（13:43、14:31、16:31 各一个），第一个占住 `Cache`，后面的搬不动也建不出缓存；三者还共享同一份 localStorage，一个窗口改的设置另一个读到的可能是旧值。

**已做的处理**：开发版改用 `%APPDATA%\MusicboxMC-dev`（打包版仍是 `%APPDATA%\MusicboxMC`）；主进程加 `app.requestSingleInstanceLock()`，第二次启动只把已有窗口 restore + focus 后以 0 退出（`app.quit()` 在 ready 之前会给出 0x80000003，改用 `app.exit(0)`）；新增 `MUSICBOXMC_USER_DATA` 覆盖，`scripts/smoke-ipc.cjs` 与 `scripts/verify-about.cjs` 各用一次性 profile 并断言 `app.getPath('userData')` 就是脚本指定的路径。

**边界**：缓存报错本身不影响功能（Chromium 退化成内存缓存），只是每次启动刷屏；切到新 profile 后开发模式开关等 localStorage 会重置一次；打包应用之间仍按 profile 单实例。

### KI-13：同乐器合并之后借道完全不运行，提示还谎称“已合并成一条主线”

**级别**：P2  
**状态**：已修复（0.4.0 第八轮）

**现象**：用户在第 4 步截图里同时看到三处矛盾——开发者读数是「MC 轨道 8 条」，「稀疏音轨借道」卡内就地提示写「当前是「同乐器合并为一条主线」：全曲已经合并，借道只在「不合并」时生效。」，检查页的合并方式一行写「借道未生效（已合并成一条主线）」。而合并出来的 8 条轨道里确实有一条只有 4 个音（源轨 11），本该能折进邻居。

**原因**：①`planLayout` 的非智能分支只在 `mergeMode === 'off'` 时调用 `attemptShare`，同乐器合并（`same`）直接跳过借道，并把 `shareOutcome` 固定写成 `'merged'`；②`'merged'` 的文案是照“强制合并成一条主线”写的，`same` 明明有 8 条轨道；③借道规划器按**源轨**统计每条轨道的音符数与容量，合并后的轨道由多条源轨组成，按源轨算会低估宿主负载。

**已做的处理**：借道改成两段——先按“不合并”的形状借，再在 `same` 合并出来的轨道上借一次。新增 `laneFoldPlan()` 以轨道为单位重新规划（每轨道取 `sourceIndices` 的首个作为代表编号、ticks 用各源轨拼接、`leadIndex` 映射到含主轨的轨道），`planLaneSharing(..., { allowCollector: false })` 禁止再新建收集轨（那会把合并特意分开的乐器混回去），`laneSharingInfo(plan, expand)` 把代表编号展开回全部源轨，界面仍按源轨号显示。被采纳的布局必须“轨道更少且 Z 不变宽”，否则保留合并结果；候选宽度跟着被采纳的布局更新。`ShareOutcome` 新增 `no-sparse`，`merged` 文案改为「已强制合并成一条主线」。实测：27 轨《鸟之诗》dMax 14 + `same` 7 轨 / Z 49 → 6 轨 / **Z 45**（跨过 48 格听距），方块 45004 → 46120；16 轨夹具 dMax 14 为 12 轨 / Z 52 → 3 轨 / Z 29；折叠后跑红石模拟器 7410/7410 音符仍全部准点。

**边界**：（第十一轮删掉了原来“只在 Z > 30 格时尝试”的门槛，现在只要合并后还有音符很少的轨道就试）`force` 仍是一条主线，不参与；`native` 乐器模式下若折完更宽会被拒（实测 native same 50 格 → `not-narrower`）；折叠会让宿主轨道的和弦行变深，方块数可能小幅上升（+2.5%），换来的是更窄的 Z 与更少的轨道；命令播放后端没有轨道排布，开关仍显示不适用。

### KI-14：手动布局超过 48 格听距时完全没有提示

**级别**：P2  
**状态**：已修复（0.4.0 第九轮）

**现象**：48 格听距只在智能分流路径上判定。把智能选择切到手动、或者直接选「不合并」生成一首 50 格宽的多轨曲目，检查页一个字的提示都没有，用户以为放得下。

**原因**：`SMART_WIDTH_UNRESOLVED` 只在 `planLayout()` 的智能分支里 push；非智能分支算完宽度直接返回。

**已做的处理**：非智能分支末尾补一次判定——超出听距时 push `{ code: 'SMART_HEARING_UNREACHED', radiusZ, limit: 48, attempted: false }`（`attempted: false` 表示没有试过合并，措辞不能写成“最窄的尝试”）。检查页与第 6 步沿用既有警告文案。第十一轮把判据从 `size.z` 改成 `hearingRadius`，警告码也随之从 `SMART_WIDTH_UNRESOLVED` 改名成 `SMART_HEARING_UNREACHED`（见 KI-15）。

**边界**：只是提示，不改布局；智能分支仍然用 `attempted: true` 区分“试过合并仍放不下”和“按规则不合并”。

### KI-15：听距拿整条 Z 跨度比 48，宽曲假报警、合并方式选错

**级别**：P1  
**状态**：已修复（0.4.0 第十一轮）

**现象**：一首歌的轨道铺得很宽，玩家站在中间，左右各 40 格都在 48 格听距内，但应用仍报“超出 48 格听距”，并且可能因为“太宽”而选择强制合并。反过来，某些真正超出听距的布局因为 Z 跨度恰好不到 48 而静默通过。

**原因**：所有听距判定都拿 `LayoutResult.size.z`（最小轨道到最大轨道的总跨度）与 `SMART_Z.audible = 48` 比较（`src/main/smartSelection.ts:8`、`decideMerge()`、`attemptShare()`、`attemptLaneFold()`、两条路径的 `SMART_WIDTH_UNRESOLVED` 推送）。而 48 格是**以玩家为圆心**的可听半径（音符盒音量 3 的线性可听距离），玩家站在中间时左右两侧各 48 格都可听，总跨度 96 格仍然成立。探针实测：《鸟之诗》27 轨、native、主轨 1 的 `size.z = 59`，触发 `SMART_WIDTH_UNRESOLVED`，但玩家 Z = 0、最远音符 31 格——半径口径下根本在听距内。

**已做的处理**：新增 `src/core/layout/hearing.ts` 的 `hearingSpot(tracks, preferredZ)`，由布局自己在轨道建完后算出 `playerZ`（主音轨红石粉那一行，强制合并时是 spine 行）与 `hearingRadius`（所有音符盒里离该行最远的 Z 距离），写进 `LayoutResult.playerZ` / `LayoutResult.hearingRadius`；注释牌、检查页、智能分流、借道/折轨道的接受条件、`SMART_RADIUS` 全部改用半径；警告码改名 `SMART_HEARING_UNREACHED`；界面读数写「最远 N 格」，不再叫「Z 向宽度」。`measureLayout()` 也返回同一组值，保证第 4 步看到的数字与最终文件一致。

**边界**：半径只看 Z。X 方向不计入合并判据。玩家沿主轨行跟随播放，界面报告该行到最远音符的横向距离，注释牌标明跟随方向。

### KI-16：region 包围盒互相重叠，同一坐标一处说空气一处说中继器

**级别**：P0  
**状态**：已修复（0.4.0 第十四轮）

**现象**：用户把生成的投影粘进游戏后说「红石断了」「借电没把红石连起来」，并给出实际文件 `AIR 鸟之诗 -Short Ver-.litematic`（2026-11-17 生成）。那次布局的一条借道走廊在 x=190 从 z=9 走到 z=19、共 9 个中继器，文件里按字节逐个读出来是连续的 9 个中继器；但游戏里只看到靠近客轨的 2 个，中间 7 格是空的。

**原因**：`sliceRegions()` 当时按「一条轨道一个 region」，并假设「轨道之间至少隔一个 trackPitch，所以 region 永不重叠」。这个假设被借道走廊打破：走廊要穿过中间轨道的 Z 行，而带深和弦的轨道包围盒很高（那次布局主轨 z=9 的和弦行占满 z=2..16）。于是主轨 region 的盒子里包含了走廊的列，它在那里存的是 `air`，而走廊所属轨道的 region 在同一坐标存的是 `repeater`——一个坐标两种说法。Litematica 每个 region 各存一份独立的稠密数组，没有跨 region 去重（`LitematicaSchematic.blockContainers` 按 region 分开），读/贴时谁先谁生效，另一方被静默丢弃。探针实测该文件有 **7610 处**这种矛盾，其中正好包含 x=190 走廊 z=10..16 的 7 个中继器（被 region_2 的空气覆盖）。

**已做的处理**：`src/core/layout/regions.ts` 重写为「按列归属 + 分行带」：每列 (x,z) 只归一条轨道；同一轨道连续若干 Z 行若 X 范围完全相同就并成一条 band；band 的 X 范围在遇到别的轨道的列时断开；最后只有当一条轨道自己的包围盒里确实没有别人的方块时才合并回单个 region（所以普通歌曲仍然是一条轨道一个 region，force 单脊柱仍然是 1 个）。回归测试 `test/regionSlices.test.ts` 三条（自造一条高和弦轨道 + 一条穿过它和弦行的走廊：任何 region 盒里都不许出现别的轨道的方块、方块一个不多一个不少、走廊三格各自只被走廊自己的 region 认领），这三条在旧实现下有两条失败。实测《鸟之诗》dMax 14 + 借道 + 取电 + 同乐器合并：18 个 region、28279 字节、矛盾坐标 0 处（旧的 7 个 region 版本是 7610 处）。

**边界**：这条修的是「文件自相矛盾」。粘贴时的实际结果还取决于 Litematica 设置（默认 `pasteReplaceBehavior = NONE`，空气不会擦掉世界里的已有方块；改成全替换时会）、粘贴顺序以及第三方工具（printer / 校验器会按盒子读空气）。文件不再有矛盾之后，无论哪种读法都不会再出现「走廊只剩 2 个中继器」。
