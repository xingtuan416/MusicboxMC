## 1. 目标

0.4.0 包含三类改动：

1. **智能声部与听感排布**：根据 MIDI 音符的力度、活跃度、复音特征等估计主音轨，把主音轨放到听感中心，副音轨按重要度围绕它排布。
2. **智能分流**：根据曲目乐器构成、空间宽度和合并后的宽度，自动给出原版/扩展音色、资源包建议和合并模式。
3. **外层 UI 打磨与全局动效**：先修正外层界面的层级、间距和状态表达，再为步骤切换、检查结果、生成进度和提示加入统一、克制的动画。

## 2. 非目标

本次不做：

- 录音级音频分析；主音轨识别只使用 MIDI 数据。
- 自动向 Minecraft 安装资源包。应用只能在导出/提示阶段建议并保存资源包。
- 自动在 Minecraft 中验证可听性。最终仍以实际粘贴和试听为准。
- 让布局模拟区块加载、服务器 TPS 或客户端声音池。
- 在初版分流规则中追求“完美识别所有曲风”。规则必须可测试、可覆盖、可继续演进。

### 2.1 术语与已确认理解

- Minecraft 原版没有 `piano` 乐器；泥土等方块触发的是 **harp / 竖琴**。项目里的“钢琴音色”指装上配套资源包后，五个扩展槽被统一成钢琴采样。
- 五个扩展槽本身就在不同八度：bass、guitar、harp、flute、bell 分别覆盖相邻音域，拼起来是 F#1–F#7。资源包不增加槽位，只统一这五个槽的音色。
- 需求文档中的“纯钢琴曲”在本文严格写作“**纯竖琴曲（需求文档：纯钢琴曲）**”，含义是所有有音高轨都使用五槽扩展竖琴。
- 来源方案里的“超出音域默认安装包”按上述语义实现为：需要跨出单个 harp 槽时推荐资源包；超出 F#1–F#7 时资源包无能为力，仍走超域警告/策略。
- “横向”已确认指 **Z 方向的轨道展开宽度**，不是 X 时间轴长度。
- 纯竖琴多音轨在 0.4.0 初版 **不合并**，即使 Z 向太宽也先保持多轨，后续实测再决定。

## 4. 功能 A：主/副音轨识别与听感排布

### 4.1 需求理解

- 用可解释的 MIDI 指标判断哪条音轨最像主旋律。
- 主音轨放在空间中心；副音轨按重要度向两侧展开。
- 玩家应能在主要听音位置附近同时听到主音轨和重要副音轨。
- 允许用户覆盖自动判断，界面必须显示“为什么选了这条”。

### 4.2 建议的统计指标

在 `analyze()` 阶段为每条轨计算并返回（不改变 `SongModel`）：

| 字段                   | 含义                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `noteCount`            | 已有字段                                                    |
| `activeSeconds`        | 从首音到末音覆盖的时长                                      |
| `meanVelocity`         | 平均 MIDI velocity（0–1）                                   |
| `maxVelocity`          | 最大 velocity                                               |
| `polyphonicOnsetRatio` | 同一时刻 >1 个音的 onset 占比                               |
| `melodicScore`         | 初版可定义为 `1 - polyphonicOnsetRatio`，只衡量“单音旋律感” |
| `activityScore`        | `activeSeconds / song.durationSec`                          |
| `prominenceScore`      | 上述指标归一化后的加权分                                    |
| `role`                 | `lead` / `support` / `percussion`                           |
| `reason`               | 供 UI 显示的解释，例如“平均力度最高 + 单音旋律”             |

**初版选择规则（已确认以响度优先）**：

1. 打击乐不参与主音轨竞争；只有全曲没有有音高轨时才允许打击乐成为主轨。
2. 在有音高轨中，`meanVelocity` 最高者优先作为主音轨。
3. velocity 接近（差值 < 0.03）时，再用 `activityScore` 和 `melodicScore` 排序。
4. 同分时按音轨索引稳定排序，保证结果可复现。
5. `prominenceScore` 用于副音轨的相对顺序，可继续使用：

```text
score = 0.50 * normalized(meanVelocity)
      + 0.30 * activityScore
      + 0.20 * melodicScore
```

**重要限制**：生成后的红石音符盒不能按 MIDI velocity 改变音量。这里的“主音轨声音最大”指它在原曲 MIDI 中最响、并且通过 Z 向居中让它离玩家最近；它不是给主轨写更大的游戏音量。用户仍可手动改选主轨。

### 4.3 空间排布

建议把“主音轨放中心”实现为布局层的可选逻辑，而不是改默认行为：

- 输入新增（暂命名）`leadTrackIndex?: number`，或更通用的 `laneOrder?: number[]`。
- 不传时保持当前行为，避免破坏现有测试和调用方。
- 传入时：
  - 主音轨放在 Z 方向中心，玩家默认站位与主轨重合：`listenerZ = leadZ`，X 在电路起点附近；
  - 副音轨按 `prominenceScore` 降序，依次放在主轨上下两侧；
  - 重要副轨紧邻，次要轨放外圈；
  - X 时间轴、重复器延迟、音符时刻完全不变。
- 布局完成后可整体平移 Z，使主轨中心落在 `z = 0`；litematic / 区域逻辑仍通过 `min` 归一化。
- 当主轨到最远轨的 Z 距离超过 48 格时，结果页提示“部分音轨可能超出一致听音范围”，并给出实际距离。

### 4.4 用户可控性

- 选轨页显示自动识别的“主音轨”标记和理由。
- 提供一个“主音轨”下拉框或单选项，允许用户改选。
- 用户改选后，后续智能排布使用用户选择，不再重新猜。
- UI 中以“智能推荐”标识和“恢复自动”动作区分自动值与手动覆盖。

### 4.5 验收

- 同一曲目重复生成，主轨和顺序稳定。
- 改选主轨后，Z 排布按新主轨重建，X/时序/音符数量不变。
- 主轨居中后，`max |z - leadZ|` 不大于旧顺序在同等条件的结果。
- 《鸟之诗》《Rush E》《happy-birthday-16.mid》和合成多轨夹具均需覆盖。

## 5. 功能 B：智能分流（替代默认选择）

### 5.1 分流树

按来源方案初版整理如下。阈值和宽度定义仍需确认。

```text
计算所选曲目分类
├─ 单乐器曲
│  ├─ 纯竖琴曲（需求文档称“纯钢琴曲”）
│  │  └─ 判断是否超出一个原生 harp 槽
│  │     ├─ 未超出：单槽竖琴，不推荐资源包
│  │     └─ 超出：扩展五槽 + 推荐钢琴采样资源包
│  └─ 其他单乐器曲
│     └─ 不推荐资源包
└─ 多乐器多音轨曲
   ├─ 宽度 > 可听范围(48)
   │  ├─ 先同乐器合并
   │  └─ 仍 > 48：全曲强制合并
   ├─ 30 <= 宽度 <= 48
   │  └─ 同乐器合并，不推荐资源包
   └─ 宽度 < 30
      └─ 不合并，不推荐资源包
```

### 5.2 已确认：“横向”指 Z 方向

“横向”指 **Z 方向的轨道展开宽度**：从最上方副轨到最下方副轨的格数，而不是 X 时间轴长度。

理由：

- 同乐器合并、强制合并减少的是并行轨道数量，实际影响的是 Z 包络。
- 48 格听距对应的是空间距离，主要在 Z 方向决定玩家能否同时听到主轨和副轨。
- X 是时间轴；合并同轨通常不会缩短 X，因此不能把它当成“合并收益”。

实现时必须注意：**合并不保证 Z 一定变小**。同乐器轨合并后，同一时刻的音符可能变成更宽的和弦，增加上下分支行；强制合并的超宽和弦也可能需要 staged 两行总线。因此三种候选布局都要重新测量 Z，最终找不到小于阈值的布局时只能选择最小者并明确提示。

### 5.3 宽度测量策略

建议用实际布局结果测量，而不是仅靠音符估算：

1. 以当前选择生成一次 `off`（不合并）布局，记录轨道 Z 包络宽度。
2. 若进入“同乐器合并”分支，再生成一次 `same` 布局，重新测宽。
3. 若仍超出，生成 `force` 布局。
4. 最终只把胜出的布局写盘；候选布局只用于规划和预览。

需要验证的成本：

- 对长曲连续跑 2–3 次布局是否可接受；
- 预览/检查步骤是否复用已经算出的候选结果，避免点“生成”时再算一遍；
- 如果成本过高，改用轻量布局探针，只计算 Z 行数，不生成方块。

### 5.4 分类规则

- **纯竖琴曲（需求文档：纯钢琴曲）**：所有参与生成的有音高轨都落到五槽扩展竖琴（`voicing.kind === 'pitch'`），且没有其他固定乐器轨；鼓轨单独处理，不计入“其他乐器”。是否使用资源包不影响分类。
- **其他单乐器曲**：所有有音高轨最终使用同一个固定乐器。
- **多乐器曲**：其余情况。
- 被用户排除的轨道不参与分类。
- 分类必须抽成纯函数并返回 `category`、理由和输入统计，便于测试和 UI 解释。

### 5.5 资源包与音域语义

当前行为必须保留：资源包只能“建议 + 保存”，不能在用户不知情时安装。它不增加音域，也不改变任何方块或时序。

准确的数据关系是：

- 单个 harp 槽覆盖 F#3–F#5。
- 五槽扩展由 bass / guitar / harp / flute / bell 分别上下移动两个八度，拼成 F#1–F#7。
- 资源包把五个槽的采样统一成钢琴音色，让完整音域听起来像同一架钢琴；真正提供音域的是五槽映射本身。
- 因此“纯竖琴曲超出单槽就推荐资源包”是成立的：
  - 只用单个 harp 槽：不推荐资源包；
  - 需要两个或更多扩展槽，但仍在 F#1–F#7：推荐资源包；
  - 超出 F#1–F#7：资源包不能解决，仍按超出音域策略处理并明确警告。
- 资源包建议跟着**乐器模式**走，而不是跟着曲目分类走：扩展竖琴音域把钢琴放在 bass/guitar/harp/flute/bell 五个槽上，不装包就是五种音色，装包才是一架钢琴，所以扩展模式推荐包；原版模式这五个槽归原生乐器，装包会把它们替换成钢琴，所以不推荐。
- 扩展竖琴音域等同于“引导用户装资源包”：不装包时五个槽是五种音色。所以只有**纯竖琴曲且需要跨出单槽**才选它，并且同时推荐资源包。多乐器曲、单乐器曲、单槽内的纯竖琴一律原版乐器，不推荐包。

### 5.6 自动选择与手动覆盖

- 新增 `smartSelection` 概念，默认开启，但只作为**默认值来源**，不会阻止用户修改。
- 用户改动受智能选择影响的设置时，UI 显示“已手动覆盖智能建议”，并允许一键恢复。
- 检查结果页展示：
  - 分类结果；
  - 宽度与阈值；
  - 采用的合并模式；
  - 资源包建议及原因；
  - 主音轨识别理由。
- 任何候选布局都复用现有音符守恒、时序不变量和强制合并校验。

### 5.7 验收

- 27 轨《鸟之诗》、`Rush E`、固定 16 轨夹具和合成分类夹具全部覆盖。
- 分类边界：29/30/47/48/49 格。
- 自动选择不改变用户手动覆盖。
- 同一输入 + 同一选项，结果可复现。
- 命令播放后端：智能分流只影响可用的选项，不悄悄改变命令播放语义。

### 5.8 追加：稀疏音轨借道（2026-11-15 用户追加）

一条只有十几个音的轨和一条几百个音的轨一样占满一条轨道：自己的 Z 条带、自己的中继器和自己的投影行。用户要求这类轨“借”已有轨道，以减少 Z 和轨道数。

- 判定：非主轨且音符数 < 阈值（默认 50，配置页可改）算稀疏。
- 顺序：借道 → 同乐器合并 → 强制合并；每个候选都跑一次真实布局并实测 Z。
- 只在未合并布局 Z > 30 格时尝试，且只有在“轨道更少且 Z 不变宽”时才采用借道。
- 宿主按 Z 顺序相邻优先，一条宿主可以收多条客串；主轨可以当宿主，但自己不借出。
- 没有宿主吃得下时，≥2 条零碎轨合成一条收集轨，且要求总音符 ≥ 50，否则保持独立轨道。
- 跨音色可借：客串保持自己单独生成时的乐器与八度，宿主不受影响（同乐器合并也改成逐源轨八度）。
- 单独开关、默认开启；手动改开关/阈值即切回手动状态。命令播放后端不适用。
- 不做逐音收集（需要把布局改成“先规划轨道再建轨”），也不做链式借道。
- 生成与第 4 步读数共用 `planLayout()`：候选布局只排一次、两处复用；读数额外返回 `shareOutcome` 与每个候选的实测宽度，用来解释“开关开了但 Z 没变”。

### 5.9 追加：主轨居中可关闭，并报告居中的宽度代价（2026-11-15 用户决定 B）

【已过时·见文首】主轨居中会把轨道按“主轨在中间、副轨交替上下”重排，当时实测更宽（16 轨夹具 40→56 格、《鸟之诗》27 轨 82→122 格），可能把本来 ≤48 格的曲目推进合并。后来查明这是 `src/core/layout/placement.ts` 的坐标别名 bug（第九轮 KI-09），修好后居中不改变宽度；下面前两条（重测不居中布局、`SMART_CENTER_WIDENS`）已在第十一轮整条删除。用户当时选择方案 B：

- `GenerateOptions.centerLead`（默认 `true`＝旧行为，不传不改变任何旧调用方布局），配置页「其它」新增「主轨居中」开关；关掉即回到历史轨道顺序与 Z 原点。
- 智能分流在**最终布局仍 >48 格**时，用同一合并方式再跑一次不居中布局；若那个更窄且 ≤48 格，给出 `SMART_CENTER_WIDENS`（`reason: 'out-of-range'`），提示“关掉居中可以回到 N 格”。
- 若最终布局能放下、但只是**因为合并才放下**（不居中且不合并就 ≤48 格），给出同一警告的 `reason: 'merge-avoidable'`，让用户知道这次合并是居中换来的。
- 两边都 >48 格（《鸟之诗》82/122）时不提示：居中并不能把曲目救回听距内，提示只会变成噪音。
- 第 6 步智能摘要追加一行“主轨居中：不居中 Z N 格（当前 M 格，检查页有提示）”。`test/centerLead.test.ts` 覆盖两类提示、关闭开关的旧几何、以及“不传 `centerLead` 与显式 `true` 结果逐项相同”。

### 5.10 追加：投影里的轨道注释，以及合并后的主音轨语义（2026-11-15 用户要求）

用户指出：投影里玩家不知道哪一条是主音轨；而且开启任意一种合并后，主音轨的说法就不太好用了。本轮拆成两件事：

- **看得见**：`src/core/layout/annotation.ts` 为每条有音符的轨道规划一块墙牌，立在电路西侧 3 格（`SIGN_COLUMN_GAP`），底座金色＝主音轨、铜色＝副轨；牌面 4 行写角色、源轨、力度与站位。牌是独立区域（`trackIndex: -2`），可以在 Litematica 里单独删除或移动。`GenerateOptions.annotateLanes`（默认开）与配置页「投影注释」开关控制，命令播放后端不适用。
- **说得对**：`TrackSkeleton` 增加 `sourceIndices`，让生成阶段能从 `lanePlan.leadTrackIndex` 反查主轨所在轨道（合并、借道、强制合并后的轨道都持有多个源轨）。全曲合并成一条主线时不再宣称独立主音轨：牌面写「全曲主线 / 站这里 / 主线行」（最初写「Z 中段」，第十一轮改），第 6 步主音轨行改为“全曲合并成一条主线，没有独立主音轨”，玩家站位站 spine 那一行（最初取主线 Z 中点，第十一轮改；两者在对称铺轨后数值恰好接近，但语义不同：Z 中点会让玩家站到没有红石粉的空行上，22 格主线站中间，最远 11 格而不是 21 格）。
- **读数一致**：`LayoutMeasure` 增加 `annotatedSigns` 与 `annotatedExtraX`；注释让 X 多 3 格，但不影响 Z 宽度与合并判定，开发者读数显示“注释 N 牌（+3 X）”。

### 5.11 追加：相邻轨道取电与红石模拟器（2026-11-15 用户要求）

用户反馈：“生成出来的轨道假如说在前面没有音后面有，总是会自己去计算音在哪，前面放中继器很稀疏却后面连着放，因为区块加载的特殊性总是会导致出现这条轨道‘断点’。”本轮分两件事：先把“断点”到底发生在哪一层测清楚，再改布局。

- **先测清楚**：新增 `src/core/sim/redstone.ts`，照 vanilla 的 `BlockRedstoneWire` / `BlockRedstoneDiode` / `BlockNote`（本机只有 1.12.2 的 MCP 反编译源）逐 tick 执行布局。结论：时间上没有问题——16 轨夹具 346/346 音符、27 轨《鸟之诗》7410/7410 音符全部落在计划 tick，和弦也仍然同时；问题在区块加载，2678 格 = 168 个区块，玩家站起点只听到 4%。
- **再改布局**：`src/core/layout/track.ts` 的 `ride` 让“首音很晚、前面这一段没有任何 tap”的轨道不再自己从 X = 0 一路递推，而是从 Z 相邻（差 2 格）的下方轨道取一次电：`(x, zBase-1)` 一个 facing 朝上的中继器引到 `(x, zBase)` 的红石粉，再从该点继续原本的布线。收益是那段“车头”整段消失：27 轨曲目省 8026 方块（-8%）与 729 个中继器，时间轴一个 tick 都不动（`test/laneRide.test.ts` 逐音符断言 `placed` 的 actual 与不取电时完全相同，并把取电后的布局跑一遍模拟器确认 346 个音符仍准点）。
- **为什么只能借相邻行**（【已过时】第七轮已改成跨行走廊）：红石粉在 T 形交叉处不会给垂直分支供电，跨轨道取电必须用中继器拐角（+2 game ticks，靠取电点西移 1 格抵消）；而红石粉相邻即连，跨过中间轨道就会点亮那一条轨道，2 层结构也没有第三层做高架。当时只做 Z 相邻两行；后来发现中继器可以自串（前一个输出格就是后一个背面，`BlockRedstoneDiode.getWeakPower`），只要走廊每格都空闲、左右没有别的中继器就不会被锁定，于是第七轮改成“跨几行就放几个中继器、每行 +1 红石 tick 并在时间轴上扣掉”。

> 注：这一版只借紧邻两行。第七轮用户报告“开了同乐器合并之后就无法取电”，已改成跨行走廊，见 §5.12。

- **开关与读数**：`GenerateOptions.laneRide`（默认开）与配置页「相邻轨道取电」开关，命令播放后端不适用、全曲强制合并时就地说明“只剩一条轨道”；`LayoutMeasure.riddenLanes` 让开发者读数显示“取电 N 条”，`GenerateResult.laneRide` 让检查页列出“Z 2←0、30←28”。

### 5.12 取电改为跨行走廊（2026-11-15 用户报告）

用户报告：“启用同乐器合并之后就无法借电了”。实测《鸟之诗》dMax 14：不同乐器合并时 27 轨 / 100956 方块 / 17 条取电；同乐器合并（8 轨 / 54040 方块）时取电条数为 **0**。

- **根因**：`chooseRide` 只认 `zBase - 2` 的宿主（正好隔一行）。同乐器合并会把多个源轨的和弦分支行叠在同一条轨道上，相邻轨道的 Z 差变成 3–5 行，取电于是全部消失；单行轨道的夹具反而还能借，所以之前的测试没发现。
- **改法**：`chooseRide` 遍历所有已建轨道，走廊＝宿主行与本行之间的每一行，每行一个同向中继器（`facing` 由上下关系决定，宿主在上方就南向）。`prevRt = 宿主该格 rt + 走廊长度`（每格 1 红石 tick）；落点与走廊格必须在`laneCells.used` 之外（该集合记录已建轨道的每个方块），走廊格左右不得是中继器（防锁定）；同一 `x` 取最短走廊。另加兜底：走廊在轨道自己的分支之前选定，若撞上本轨道分支（同一格写两个方块会静默失效）就退回自建车头。
- **实测**：不合并 100956 → 70410 方块（17 条取电）；合并 54040 → 49174（3 条，8 轨 / Z 39 都不变）；夹具 dMax 8 5066 → 4454（4 条）。红石模拟器：不合并与合并两种布局下《鸟之诗》7410/7410 音符全部命中计划 tick，零提前、零延后、零丢失。
- **测试**：`test/laneRide.test.ts` 改为断言“跨过中间每一行都有同向中继器”，新增“合并后仍然取电”与“合并 + 走廊时模拟器仍逐音符准点”两条。
- **教训**：第一版探针用最终布局的**全部**方块算列占用，把 guest 自己的车头也算成障碍，得出“没有可用列”的错误结论；探针必须排除被测对象自身。

## 6. 功能 C：外层 UI 打磨与全局动效

用户已确认“外层 UI 不是很完美”，因此本阶段不是单纯加动画，而是先做界面打磨，再加动效。

### 6.1 外层 UI 审计与打磨

逐页检查八步流程、配置面板、检查结果、结果页和对话框：

- 视觉层级：标题、说明、主按钮、危险/次要操作是否一眼可分。
- 间距与对齐：卡片内边距、标签与输入框基线、分页和滚动条位置是否统一。
- 状态表达：空态、加载、成功、失败、警告、禁用和“已手动覆盖”是否明确。
- 响应式：1280×860 默认窗口、900×600 最小窗口、高 DPI 下不溢出、不遮挡。
- 可访问性：键盘焦点可见、对比度、点击区域、`prefers-reduced-motion`。
- 一致性：颜色、圆角、阴影、字号、按钮高度、图标尺寸使用同一套 token。
- 性能：不为视觉优化引入长曲预览的重复全量绘制。

原则：以现有米色/纸张式视觉语言为基础做精修，不重做品牌，不引入框架或打包器。

### 6.2 动效范围

建议覆盖：

- 步骤切换的进入/退出；
- 卡片、检查结果项和图标的轻微上浮/淡入；
- 生成进度、按钮按下、通知出现；
- 预览首次出现或布局切换的淡入；
- “在红石布线里定位”后的高亮脉冲。

不覆盖：

- 红石格子的持续呼吸/闪烁；
- 大规模 canvas 模糊、阴影或逐格动画；
- 会改变布局尺寸或触发连续重排的动画。
- 红石预览内部的逐格动画。

### 6.2 设计约束

- 使用 CSS transition / Web Animations，动画只作用 `opacity` 和 `transform`。
- 统一时长：短反馈 120–180ms，步骤切换 200–260ms；使用同一 easing token。
- 遵循 `prefers-reduced-motion: reduce`，关闭位移动画但仍允许即时状态切换。
- 动画不阻塞输入；生成中仍可取消/返回（如果当前流程支持）。
- `verify:ui` 截图必须等待动画稳定，或在该脚本里注入 reduced-motion。

### 6.3 验收

- 八步流程在默认和最小窗口尺寸下无横向溢出、无遮挡、无 console 错误。
- 空态、加载、成功、失败、警告和手动覆盖状态都有明确文案与视觉区分。
- 动画不导致长曲预览重复全量重绘。
- 用户实测开关步骤、检查页、结果页和定位动作，确认“布局更完整、有动效但不拖沓”。

## 10. 风险

1. **主轨识别误判**：MIDI velocity 不是游戏内实际响度，生成的音符盒也不能按 velocity 调音量；必须允许覆盖并展示理由。
2. **“中心”依赖玩家站位**：已确认以主轨中心为听音位置；若玩家偏离主轨，听感优势会减弱。
3. **资源包被误解为扩展音域**：五槽映射本身提供 F#1–F#7，资源包只统一这五个槽的采样；超出 F#1–F#7 仍无解。
4. **合并不保证 Z 变窄**：同乐器轨合并可能把同时音变成更宽的和弦，强制合并可能触发 staged 总线；必须实测候选 Z 后再选择。
5. **自动合并改变输出语义**：强制合并会增加全曲延迟和结构高度，UI 必须提前显示。
6. **多次布局成本**：长曲可能明显变慢，需复用候选结果或改用探针。
7. **轨序变化破坏测试**：默认关闭新 lane order，只有智能模式启用；旧测试保持原语义。
8. **动画影响可访问性与自动化**：必须支持 reduced-motion，并在 UI 验证中固定等待条件。
9. **规则初版不等于最终版**：阈值和权重应集中在配置对象中，不散落在 UI 或布局代码里。

### 5.13 同乐器合并后也借道（2026-11-15 用户报告）

**触发**：用户第 4 步截图里，开发者读数写「MC 轨道 8 条」，借道卡内提示却写「当前是「同乐器合并为一条主线」…借道只在「不合并」时生效」，检查页写「借道未生效（已合并成一条主线）」。

**根因**：`planLayout` 的非智能分支只在 `mergeMode === 'off'` 时调用 `attemptShare`，`same` 跳过借道并把 `shareOutcome` 固定写成 `'merged'`；借道规划器按源轨统计容量，合并后的轨道由多条源轨组成，宿主负载会被低估。

**实现**：新增 `laneFoldPlan()` 以轨道为单位重新规划（代表编号取轨道的第一个 `sourceIndex`、ticks 为各源轨拼接、`leadIndex` 映射到含主轨的轨道）；`planLaneSharing(..., { allowCollector: false })` 不再新建收集轨；`laneSharingInfo(plan, expand)` 把代表编号展开回全部源轨；`attemptLaneFold()` 只在“轨道更少且 Z 不变宽”时被采纳，候选宽度同步更新为被采纳的布局。

**结果**：27 轨《鸟之诗》dMax 14 + `same` 7 轨 / Z 49 → 6 轨 / Z 45、45004 → 46120 方块；16 轨夹具 dMax 14 12 轨 / Z 52 → 3 轨 / Z 29；折叠后红石模拟器 7410/7410 音符全部准点。

**测试**：`test/laneSharing.test.ts` 16 条（新增 fold、`no-sparse`、`force` 不参与）、`test/laneRide.test.ts` 8 条（新增折叠后逐音符准点）。门禁 48 文件 / 354 用例。

**教训**：候选宽度必须跟着被采纳的布局更新，否则界面显示的是被丢弃的那个宽度。

### 5.14 主轨居中“拉宽”是坐标别名 bug（2026-11-17 审计发现）

**触发**：用户问「功能 A：主/副音轨识别与听感排布完整实现了吗」；随后 fork 的只读审计逐条对照 10 条需求，发现居中布局里每个音符盒都偏离自己的红石行。

**根因**：`src/core/layout/placement.ts` 的 `place()` 直接返回传入的格子对象；`src/core/layout/track.ts` 的 `putNote` 把同一个 `notePos` 既交给 `place()` 又存进 `PlacedNote.notePos`。`translateTrackZ()` 居中时先平移 `placement.pos.z`（同一对象）再平移 `note.notePos.z`，同一格被平移两次。探针：不居中 0/346 偏移，带 `laneOrder` 346/346 偏移、最远 19 格、跨区域重复 571 格，红石模拟器 0 个音符响。KI-09 的“居中让 40 → 56 格”完全是它造成的。

**实现**：`place()` 改为 `{ pos: { ...pos }, ... }` 并注释引用共享风险；`test/centerLead.test.ts` 两条断言改为“居中不改变宽度且不报 `SMART_CENTER_WIDENS`”；新增 `test/layoutGeometry.test.ts`（音符位置＝方块位置、行内无重复、轨道顺序不改宽度、居中布局跑模拟器 346/346 准点）。同轮把主轨下拉的手动选择并入 `selectionSignature()`（不再顺手关掉智能推荐，但下一步会按新主轨重测），并在非智能分支补 `SMART_WIDTH_UNRESOLVED`（`attempted: false`，`KI-14`）。

**结果**：夹具 40 / 40、鸟之诗 82 / 82、同乐器合并后 38 / 38（居中 vs 不居中）；检查页 done 页 Z 从 21 变 12（借道 + 取电都在，尺寸是真实几何）。

**测试**：全部 49 文件 / 358 用例；`npm run verify:ui` 通过（无 console 错误、无横向溢出）。

**教训**：`place()` 这类底层构造器不要转发调用方的可变对象；凡是“布局整体平移”的代码，都要有一条断言同一格只出现一次的测试兜底——方块数对不上时没人会发现，因为总数没变。

### 5.15 听距改半径口径 + 主音轨恒在 + 对称铺轨（2026-11-18 用户指出）

**触发**：用户连续指出四点——「声音距离是 48 格没错，但玩家站在中间，左右各 40 格都听得见」、「智能分配只是帮用户快速挑选项，开关它不该改变结果」、「强制合并成一轨道就不会有借点，选强制合并后借道和取电在前端应该直接消失」、「所有情况下都应该有主音轨，只考虑力度」，另有「确认主轨道后应指定玩家站主轨道的哪一条 Z 轴，最好是有红石粉那一行，且玩家所站处于投影中心」「确定玩家 Z 后即可据此排出轨道顺序」「借道要保留原始力度」。

**根因**：①听距判定拿 `LayoutResult.size.z`（最小到最大轨道的总跨度）与 `SMART_Z.audible = 48` 比，而 48 是以玩家为圆心的可听半径——《鸟之诗》27 轨 `size.z = 59` 就报警，实际玩家站中间、最远音符 31 格；②主音轨只在开智能或手选过时存在，关掉后注释牌写「未指定主轨」、站位退到 Z 中点；③`orderTrackInputs` 把主轨放中间再两侧交替，导致 laneOrder 的优先级与“离玩家的距离”不一致（实测 laneOrder [2,0,1] 得到距离 0/4/2）；④借道/折轨道的接受条件是“Z 不变宽”，与“听距”无关。

**实现**：新增 `src/core/layout/hearing.ts`（`hearingSpot(tracks, preferredZ)` → `{ playerZ, hearingRadius }`），`LayoutResult` 新增 `playerZ` / `hearingRadius`；`SMART_RADIUS = { compact: 30, audible: 48 }`，`SMART_HEARING_UNREACHED` 取代 `SMART_WIDTH_UNRESOLVED`，`decideMerge()`、`attemptShare()`、`attemptLaneFold()`、两条路径的警告、`LayoutMeasure`、检查页读数全部改用半径；`SMART_CENTER_UNREACHED` 与“重测一次不居中布局”的整条管线删除。`prominence.ts` 改成纯力度排序（`meanVelocity` → noteCount → index），删 `VELOCITY_TIE` 与打击乐排除，`LeadBasis` 只剩 `velocity`；`generate()` / `measureLayout()` 一律 `buildLaneOrder()`。Z 分配改成双侧游标（`aboveLimit` / `belowLimit` / `preferAbove`），站立轨道固定 `zBase = 0`、其余按优先级放到更近一侧，`TRACK_SPLIT` 沿同侧追加；`centerLead` 语义改为“按优先级排 / 按文件顺序排”，未排轨道时用 `GenerateOptions.standTrackIndex` 指定站立行。借道/折轨道接受条件改为“轨道更少 且 半径 ≤ max(原半径, 48)”。force 合并时配置页 `hidden` 掉 `#laneShareCard` / `#laneRideCard`，后端忽略这两个选项。

**结果**：实测《鸟之诗》dMax 14（`measureLayout`，extended）：不合并 27 轨、跨度 82、**半径 42**、玩家 Z 0、100956 方块；`same` 7 轨、半径 18、49554；`same + 借道` 6 轨、半径 18、48288（applied）；`force` 1 轨、跨度 22、半径 11、玩家 Z 10（正好站 spine 行）、40858；取电 27 轨、半径 42、73958。16 轨夹具：不合并半径 21、`same` 18、`same + 借道` 3 轨 15、`force` 1 轨半径 10 / 玩家 Z 9。红石模拟器复测：不合并、`same`、取电三种布局各 7410/7410 音符准点；`force` 布局 1378 列“同列 tick 全同、X 递增 tick 不回退”。

**测试**：新增 `test/smartEquivalence.test.ts` 13 条（手写 SMF 造宽曲，3 曲型 × dMax 8/14 × laneSharing 开/关，断言智能开关与手挑同一组选项的 regions/placed/方块/警告完全相同）；`test/centerLead.test.ts`、`test/trackSpacing.test.ts`、`test/trackOrder.test.ts`、`test/prominence.test.ts`、`test/smartGenerate.test.ts`、`test/measure.test.ts`、`test/laneAnnotation.test.ts`、`test/laneRide.test.ts` 按新几何重写。门禁 50 文件 / 373 用例。

**教训**：①“宽度”与“可听性”是两个量，凡是要跟 48 比较的地方都必须用半径；②排序决定布局时，排布顺序必须与排序依据一致，否则“第二优先”可能比“第三优先”更远；③力度的平局窗口（0.03）会让“只按力度”变成“按综合分”，用户要求单一依据时要把权重整段删掉而不是调小。

### 5.16 投影分区互相重叠，借道走廊被当成空气覆盖（2026-11-18 用户实测发现）

**触发**：用户把生成的投影粘进 1.21.8 后截图说「红石断了」「这是借电的问题」，并给出实际文件与一句「如果你的测试没测出来，那肯定是你测试的问题」。

**根因**：`sliceRegions()` 按「一条轨道一个 region」切，注释里写着「轨道之间至少隔一个 trackPitch，所以 region 永不重叠」——这条假设在取电走廊出现后失效。走廊穿过的中间轨道如果有深和弦，它的包围盒会把走廊的列包进去并存成 `air`，与走廊所属 region 的 `repeater` 冲突。用户文件里这类矛盾 7610 处，正好复现「x=190 九格走廊只剩两格」。

**实现**：`src/core/layout/regions.ts` 改成按列归属切（每列唯一 owner），同一轨道连续同 X 范围的 Z 行并成 band，band 在遇到别的轨道的列处断开；只有包围盒干净时才合并回单 region。新增 `test/regionSlices.test.ts` 三条回归（旧实现下两条失败）。

**结果**：《鸟之诗》dMax 14 + 借道 + 取电 + 同乐器合并 → 18 regions / 28279 字节 / 矛盾坐标 0（原来 7 regions / 24845 字节 / 7610 处矛盾）；不合并 27 轨 → 27 regions、方块数等于 placed、两两盒重叠 0。

**教训**：①「XX 之间至少隔一个间距，所以永不重叠」这类几何断言，一旦有跨行结构（走廊、注释牌、总线）就会被打破，必须按「列归属」这种更细的粒度证明互斥；②测试如果只仿真内存里的 `LayoutResult`，看不到写入器的区域裁剪与覆盖——必须把写出的文件读回来再仿真（`test/litematicElectrical.test.ts` 已有的做法）；③文件级不变量值得单独测：同一个坐标只能有一个 region 声明非空气。
